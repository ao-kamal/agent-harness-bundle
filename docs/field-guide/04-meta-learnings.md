# 04 — Fifteen Meta-Learnings

Chapter 01 said the strictness in this bundle's rules is paid for, not decorative. This chapter is the receipt: fifteen specific, transferable lessons, each one earned by something going wrong once. A few of these were already told as stories in chapter 03, because they're Windows/WSL-specific; they're repeated here briefly, in the same numbered list as the rest, because the point of this chapter is the full set, not just the ones with a good story attached. The goal isn't to memorize fifteen rules — it's to recognize the *shape* of each one, so you notice it happening in a context this list never anticipated.

**1. Enforcement-over-structure has a carve-out, and knowing which side you're on is the actual skill.**
If you catch yourself writing "you MUST include X" to patch a system that isn't producing X on its own, that's usually a sign to fix the system, not to write a sterner instruction. That's true for anything you control the upstream of — a prompt, a schema, a piece of code. It stops being true exactly once: rules that govern an agent's own runtime behavior, where there's no upstream layer left to fix, because the rule *is* the upstream. There, absolute language ("NEVER," "no exceptions") is the correct engineering choice. The test: is there a layer above this rule where a structural fix would make the rule unnecessary? If yes, fix that layer. If no, write the rule strictly and mean it.

**2. Shell strings crossing OS or shell boundaries are not string-safe by default.**
Any time a command string has to pass through more than one parser — Windows shell to `wsl.exe` to WSL's bash, say, or Windows to PowerShell to some nested tool — assume that whatever quoting guarantees hold in any one of those layers don't survive the handoff intact. The fix isn't more careful quoting. It's not passing the content as a string at all: a heredoc through standard input, or an argument list passed directly to a process, gives the intermediate layers nothing left to re-interpret. Chapter 03 has the full story and the exact trigger list for when this applies.

**3. Silent failure is worse than loud failure, and Windows produces it constantly.**
A chained Windows move command that reports success while the file never moved. A piped install script that reports success even though the download that fed it failed. A heredoc-adjacent loop whose variable silently comes back empty. None of these raise an error — they just quietly do the wrong thing, and you find out several steps later, looking at output that seemed fine until it obviously wasn't. Build the habit of asking "would I actually notice if this silently failed?" before trusting anything new — if the answer is no, that's the thing to harden first.

**4. Streamable-by-design is something you build in, not a fix you apply after something looks stuck.**
A script that prints short progress lines runs fine when you watch it directly in a terminal. Redirect that same output to a file or a pipe — exactly what happens when a task runs in the background — and most language runtimes silently switch from flushing every line to buffering several kilobytes before writing anything at all. The script isn't stuck. It just looks identical to stuck, for minutes at a time, to anyone tailing the log. Fix this at the point you write the script (explicit line-buffering, explicit flushes on the lines you actually care about), not at the point someone's staring at a silent log wondering if it died. A useful design check: if this script were backgrounded and tailed right now, would the first progress line show up within a few seconds?

**5. Two or three security gates can look like one flag.**
A single "skip permissions" flag defeats *runtime* confirmation prompts. It does not defeat a separate startup-time trust dialog, and it does not defeat a separate sensitivity gate that some tools apply specifically to certain paths (this bundle's example: `.git/`). When something "still gets blocked despite the bypass flag," the useful question is never whether the flag is broken — it worked exactly as documented. The useful question is which of the several independent gates you're actually looking at, because each one needs its own answer. Chapter 03 covers this concretely for this bundle's stack.

**6. When two status surfaces disagree, trust the cheaper-but-realer one, and climb a ladder.**
A tool's own high-level "here's the current state" summary can be wrong — miscounted, stale, or reporting low-confidence guesses — even while the raw data underneath it is completely fine. The generalizable move, whenever a summary and reality seem to disagree: check the realest, cheapest signal first (an actual process list), then the next cheapest (raw output/logs), then real-world evidence of work happening (files changed, commits made), and only then trust the tool's own aggregated verdict. This ladder generalizes to debugging almost any orchestration layer, not just the multi-agent one this bundle installs.

**7. Tool knowledge decays even for tools you already know well.**
Flags get repurposed. Defaults get changed silently between versions. A README and the actual shipped binary drift apart — this bundle has at least one tool whose documented flag doesn't match what the binary actually accepts. "I used this last week" is a claim about last week, not about right now. The discipline of re-reading canonical reference before each real use — not relying on memory, however recent — is what catches drift before it costs an hour of confidently wrong guessing. This is the entire reason this bundle installs a dedicated skill for nearly every tool and insists it gets read first.

**8. Naming and pre-rejecting specific rationalizations is a legitimate way to write a rule.**
When a rule keeps getting quietly talked around — "it's just one variable," "this case is too simple to bother," "I'll just escape the special character" — the fix usually isn't a longer or sterner rule. It's naming the specific rationalization in the rule itself and shooting it down explicitly, so it's no longer available as a fresh-sounding argument next time. You'll see this technique used directly in this bundle's own configuration (`config/rules/wsl-patterns.md` lists several rationalizations by name, each one already tried and already failed) — it's not padding, it's closing a door that would otherwise reopen.

**9. A protocol-level ceiling can look exactly like a tuning problem, and isn't one.**
Some performance walls aren't about your code or your configuration at all — they're a property of a translation layer sitting underneath both. This bundle's example: WSL's compatibility bridge for reading Windows files makes certain database operations 10 to 100 times slower than the same operations on native storage, no matter how the database itself is tuned. Recognizing "this smells like a physics limit in the layer underneath me, not a setting I haven't found yet" saves a lot of wasted tuning effort chasing a knob that was never going to fix it.

**10. Model and version staleness hides in tool defaults, silently.**
A tool compiled months ago can ship a hardcoded default (a model name, a version pin) that was current the day it was built and has quietly gone stale since — and the tool itself has no way of knowing better, because nothing tells it the world moved on. The habit worth building: before trusting "just use the default" for anything version-sensitive, check what's actually current right now, out loud, every time — not just the first time you learned the default might be stale.

**11. Asymmetric, stateful networking defaults compound into bugs that look impossible.**
Two networking quirks that are individually minor can combine into something that looks like nonsense: a name that resolves to two different addresses depending on which one gets tried first, plus a mode that silently mirrors one side's listening ports onto the other. Chapter 03's `127.0.0.1`-not-`localhost` story is this bundle's concrete example — a connection that hung instead of failing, for reasons that had nothing to do with the actual service being probed. The lesson: know your networking layer's actual defaults before you spend an afternoon debugging a service that was never broken.

**12. Match the transfer tool to network conditions, not just to what's already installed.**
When two different download tools fail identically and repeatedly on the exact same file, the honest read usually isn't "this file is bad" or "both tools are broken" — it's that neither tool resumes a broken transfer, and the network you're on breaks transfers. Recognizing "the same failure across two different tools on the same path" as a signal to change *strategy* (a resumable transfer method), rather than just retrying the same approach harder, is the transferable insight. Chapter 03 covers the specific tool this bundle uses for it.

**13. Default to installing a missing dependency. Only work around it if installing genuinely fails.**
The instinct to reach for a workaround — parsing text with regular expressions instead of installing a real parser for the format, say — produces something that's harder to maintain and more fragile than just installing the real thing would have been. Treat the workaround as a fallback for when installation actually fails, not as the first move, and say so explicitly on the rare occasion you do have to fall back.

**14. Separate "reference material a tool needs in order to run" from "knowledge a person needs in order to think."**
A tool's own bundled reference folder should hold the narrow, mechanical things it needs to operate correctly — a dispatch table, a format spec, a hook pattern. Genuinely reusable methodology and research belong somewhere a person can find them independent of any one tool that happened to need them first — a proper notes system, not a folder buried inside a specific tool's own directory. Conflating the two makes both harder to find later: the tool's folder bloats with things that aren't its job, and the methodology becomes invisible outside the one context that originally produced it.

**15. Derive your defaults from your own actual setup, and show the derivation — don't just inherit someone else's number.**
Any fixed constant borrowed from someone else's specific environment — a screen resolution, a memory limit, a timeout — was almost always calculated from *their* hardware, not yours. The useful habit isn't memorizing the number; it's redoing the two-line calculation that produced it for your own setup, and writing that calculation down next to the number so the next person (including future-you) can redo it too instead of quietly inheriting a number that made sense for a different machine.
