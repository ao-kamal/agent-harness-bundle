# NTM Swarm Operations

Split from the global CLAUDE.md 2026-07-30 (gotchas preserved verbatim; new swarm conventions appended at the end).

Always invoke the `ntm` AND `vibing-with-ntm` skills BEFORE driving a swarm. They contain the canonical observability patterns, stuck-pane recovery ladders, and operator-loop recipes — agents that skip them re-derive a lot of friction badly. The single most useful discovery command (use it BEFORE parsing human-help): `ntm --robot-capabilities` returns the machine-readable schema of every robot-mode flag.

For the **workflow mental model** — who plays what role (user, main CC as dispatcher-vs-operator, swarm panes, dashboard window placement), the three skill flavors (ongoing implementation vs one-shot analysis vs operator recipes), and when to use `ntm controller` vs main-CC-as-operator — see `ObsidianVault/References/ntm-swarm-workflow-mental-model.md`. Read it BEFORE dispatching a swarm if you haven't seen it before.

Recurring gotchas that the skills already document but agents miss:

- **`ntm` is WSL-only — there is no Windows binary.** Always invoke via WSL using the canonical heredoc form (rules/wsl-patterns.md); inline `bash -lc 'simple-cmd'` only for single trivial commands. Plain `ntm` from Windows Git-Bash returns "command not found".
- **`ntm activity` / `ntm health` lag reality** — they have shown everything as stale ("56 years ago"). Trust `--robot-is-working` and `--robot-agent-health` over them — but those have their own failure modes (see below); when in doubt, climb the Liveness Truth Stack.
- **`--robot-is-working` summary count and confidence can lie.** The `summary.total_panes` field has shown 5 when 6 panes existed; per-pane `state: UNKNOWN` with confidence 0.5-0.6 has appeared while `--robot-tail` clearly showed the agent thinking. The per-pane data is usually correct; the summary aggregates and low-confidence verdicts are not. When two surfaces disagree, climb the Liveness Truth Stack: `tmux list-panes -F '#{pane_current_command}'` (real PIDs) → `tmux capture-pane -p` (real buffer) → `git log --since` / `pgrep cargo|rustc` (real work) → `--robot-is-working` (provider-side state).
- **`ntm send` defaults to CASS dedup check** which prompts interactively and silently blocks scripted dispatch. Use `--robot-send` (non-interactive by design) for swarm loops, or pass `--no-cass-check` to plain `send`.
- **`ntm --robot-send` requires `--msg` or `--msg-file`** — there's no stdin form, the call errors out without one. For dispatching marching-orders to multiple panes, point `--msg-file` at the orders file and loop with `--panes=N`.
- **Per-pane interrupt is `--robot-interrupt=SESSION --panes=N`** (NOT `ntm interrupt --pane=N` — the subcommand is whole-session-only).
- **`ntm copy` uses `session:pane` syntax**, NOT `--pane=N` — different convention from `ntm send`. Example: `ntm copy myproject:1 --last 50`.
- **Stuck-pane detection** — don't trust pane buffers alone; use the Liveness Truth Stack from vibing-with-ntm (tmux pid → capture-pane → git log → robot-is-working). "Cogitated for 35m" is a display artifact, not activity.
- **`ntm --robot-wait=SESSION --wait-until=idle --timeout=10m`** is the canonical wait-for-readiness pattern, but **it returns instantly when panes are post-startup-pre-prompt** — just-spawned agents register as `WAITING` immediately even if their CLI hasn't finished booting. Pair `--robot-wait` with a `tmux list-panes -F '#{pane_current_command}'` check that every pane is running the agent CLI (claude/codex/gemini, not bare zsh) before dispatching marching orders.
- **`ntm kill <session>` defaults to interactive y/N confirm** and silently aborts in scripted contexts. Always pass `--force` (or `-f`).
- **`ntm kill` does NOT kill the underlying agent processes.** The tmux session dies but `claude`/`codex`/`gemini` PIDs survive as orphans and keep refreshing tokens against the shared `.credentials.json`. Verify with `pgrep -af claude` (or the relevant agent name) and follow up with `pkill -9 -f "/root/.local/bin/claude"` before any `caam` swap or fresh spawn — otherwise you race the orphan auth-refresh loop and corrupt credentials.
- **`ntm spawn`'s `--no-cass-context` and `--no-recovery` are different code paths.** The first disables cm-memory context injection; the second disables session-recovery prompt injection. The cm-memory `context deadline exceeded` failure typically fires during _recovery_, not context — so `--no-cass-context` alone won't prevent it. If you've ever seen the cm timeout, pass BOTH flags on the next spawn.
- **Prompt history is retrievable** via `ntm history search "..." --session=myproject`.
- **`ntm spawn --cc=N` (no `:variant` suffix) defaults the model from a hardcoded table baked into the ntm binary at build time** — the default silently lags the actual latest release (confirmed via `ps -eo cmd`: panes spawned with a bare `--cc=3` carried a model string several releases stale; the pinned "latest" this rule once named has itself gone stale twice, which is the point). The `~/.config/ntm/config.toml` agent template only injects `--model` when `.Model` is populated; the binary populates it from the stale default table. **Before ANY `ntm spawn` (or respawn / `--robot-restart-pane` / `caam` swap that reissues launch flags), confirm the model with the user out loud:** state the version that would land if you do nothing, name the latest model per CURRENT system-info (never from memory), and ask them to pick. Pass the chosen model explicitly via the variant suffix (`--cc=3:<model-id>`). This rule applies even when the user has already authorized the spawn — the count/flags are authorized but the model has to be re-confirmed because the silent stale-default risk doesn't get cheaper to fix later.
- **Kimi panes — cheap workhorse / Claude-limit fallback in the swarm.** "Kimi panes" are ordinary `cc` panes routed to Moonshot's **Kimi Code subscription** instead of Anthropic. Routing is handled by `/root/.local/bin/cc-router`, set as the `[agents].claude` launch template in `~/.config/ntm/config.toml` (original backed up to `config.toml.bak`). The router inspects the pane's `--model`: `kimi*` → Kimi env (base URL + `ANTHROPIC_AUTH_TOKEN`) with all `ANTHROPIC_DEFAULT_*_MODEL` tiers = `kimi-for-coding` + `CLAUDE_CODE_AUTO_COMPACT_WINDOW=262144`; `k3*` → same endpoint with OPUS/SONNET tiers = `k3[1m]` + 1M window (`CLAUDE_CODE_AUTO_COMPACT_WINDOW=1048576` + `CLAUDE_CODE_MAX_CONTEXT_TOKENS=1048576`); `k3-256k*` → K3 at 256k. It then `exec`s the real `claude`; any other model → explicitly unsets those vars (clean-slate) and launches normal Claude with subscription/OAuth env untouched. (k3 branches added 2026-08-06 per Kimi's official Claude Code config; pre-k3 original at `cc-router.bak`.) Vocabulary → command (translate these for the user; they never type ntm flags):
  - "spawn N kimi panes" → `ntm spawn <proj> --cc=N:kimi-for-coding`
  - "M cc and N kimi panes" → `ntm spawn <proj> --cc=M:<current-claude-model> --cc=N:kimi-for-coding`
  - "spawn N k3 panes" (K3 @ 1M context — **Allegretto+ plan only**; `kimi-for-coding` is 256k on ALL plans) → `ntm spawn <proj> --cc='N:k3[1m]'` — quote it, zsh globs brackets. On Moderato, k3 is endpoint-capped at 256k: use `:k3-256k` there instead. `k3[1m]` is an alias form (auto-maps to latest K3), so the spawn-model re-confirm rule doesn't apply to k3 panes either. K3@1M burns ~2x quota vs k3-256k.
  - Kimi panes are `cc` panes to ntm, so restart/tail/mail/beads/operator-loop all work unchanged.
  - Model string is the stable alias `kimi-for-coding` (auto-maps to the latest Kimi backend) — so the spawn-model re-confirm rule above does NOT apply to Kimi panes (always-latest by design, nothing stale to catch). Use a pinned `kimi-*` model id only to deliberately pin a version. **Never** spawn Kimi with a bare `--cc=N` (the stale-default injects a `claude-*` model that Kimi 400s) — always the `:kimi-for-coding` variant.
  - Endpoint `https://api.kimi.com/coding/`; key at `C:\Users\USER\.config\kimi\key` (WSL reads `/mnt/c/Users/USER/.config/kimi/key`). Both `ANTHROPIC_API_KEY` (x-api-key) and `ANTHROPIC_AUTH_TOKEN` (Bearer) authenticate; we use `ANTHROPIC_AUTH_TOKEN` to avoid Claude Code's API-key approval prompt in unattended panes.
  - **Billing/quota:** flat — all clients share one membership quota (~300–1,200 req/5h, ~2k/week, up to 30 concurrent), NOT per-token metered. Separate key-based pool, NOT OAuth/caam — so Kimi panes keep working when Claude limits are exhausted, but `caam` cannot rotate you out of a Kimi quota wall (hard weekly cap).
  - **Operator blind spot:** ntm's `--robot-health-oauth` / rate-limit surfaces are Claude/OpenAI-shaped and will NOT detect a Kimi pane hitting its cap — watch for HTTP 429 / quota errors in the pane buffer instead.
  - **Windows (outside ntm):** a "Claude (Kimi)" Windows Terminal profile (fragment at `…\Windows Terminal\Fragments\Kimi\kimi.json`, which runs `~/.config/kimi/kimi-env.ps1`) opens a tab with the Kimi env pre-set; run `claude` / `claude -c` / `claude --resume` there. Resume/history/MCP/settings work normally — sessions are stored per-project on disk, model-independent. Claude Code's native `/model` picker CANNOT switch to Kimi (base URL + key are session-global) — provider switching is per-tab/session by design.
- **Grok Build panes — ntm 1.29+ has native spawn AND send (ntm#251 closed).** `ntm spawn <proj> --grok=N[:model[:effort]]` launches official `grok --always-approve`. `--robot-send`, interrupt, restart, assignment, and health all work against the real Grok TUI (verified on grok 1.0.5). Persona injection stays fail-closed: the Grok CLI has no system-prompt flag. Vocabulary → command:
  - "spawn N grok panes" → `ntm spawn <proj> --grok=N`
  - Prefer native `--grok` over the old SuperGrok-via-Claude-Code trick (`--cc=N:grok-4.6` + CLIProxyAPI `127.0.0.1:8317`). Keep that path only if Windows TUI markers drift from the macOS capture ntm was trained on (then dump `tmux capture-pane` and file a follow-up)
  - Token/proxy files for the fallback: `C:\Users\USER\.config\xai\proxy-token` and `grok-env.ps1`. Do not put the token in ntm config or in git
  - Operator sits in Grok Build. Shared brain is still `~/.claude` (see `harness-shared.md`)
- **Antigravity panes — native `agy` subscription, no CLIProxy.** ntm 1.29 launches `--agy=N[:model]`. WSL sees `agy` via `/usr/local/bin/agy` which execs the Windows `agy.exe` (interop, Google OAuth stays on the Windows account). Do **not** point agy at CLIProxy / a fake Anthropic base URL — ban risk. Model is `--model` from `agy models`. Default if omitted: Gemini 3.7 Flash (High). Vocabulary → command:
  - "spawn N agy panes on 3.1 pro high" → `ntm spawn <proj> --agy=N:gemini-3.1-pro-high`
  - "2 opus thinking + 2 flash" → `ntm spawn <proj> --agy=2:claude-opus-4-6-thinking --agy=2:gemini-3.7-flash-high`
  - Live ids (re-run `agy models` before spawn; they drift): `gemini-3.7-flash-high|medium|low`, `gemini-3.6-flash-*`, `gemini-3.5-flash-*`, `gemini-3.1-pro-high|low`, `claude-sonnet-4-6`, `claude-opus-4-6-thinking`, `gpt-oss-120b-medium`
  - `--gmi` is leftover Gemini CLI, not the Antigravity sub. Use `--agy`
  - Always pass the model id. A bare `--agy=N` silently pins Gemini 3.7 Flash High
- **`.git/` permission dialogs cascade across panes during any concurrent-commit swarm — and `--dangerously-skip-permissions` does NOT bypass them.** Claude Code has a SEPARATE per-path "sensitive file" gate for `.git/` access that fires the FIRST time each pane touches `.git/`. With 3-6 agents committing in parallel you will see 3-6 dialogs in the same tick, each blocking the holding pane until resolved. Three dialog variants observed (April 2026 alen-sultanic-swipe swarm — every commit-heavy phase tripped them):
  - `Do you want to proceed? 1.Yes / 2.Yes,and always allow access to .git/ from this project / 3.No` → `tmux send-keys -t SESSION:0.N "2" Enter`. Pick "2" (always-allow); "1" makes the dialog re-fire on every subsequent git operation in that pane. The "always allow" scope is per-project, not global, so the blast radius is bounded.
  - Per-command variant for specific git operations like `git add` / `git stash drop` / `rm .git/index.lock`: `Do you want to proceed? 1.Yes / 2.Yes,and don't ask again for similar commands in /mnt/.../<project> / 3.No` → also "2" Enter, same reasoning.
  - Simple Yes/No "remove stale index.lock?" or "git stash drop?" with no always-allow option → "1" Enter.
    Every cron tick during commit-heavy phases MUST scan all panes for these dialog texts (look for `Do you want to proceed?` and `Esc to cancel · Tab to amend · ctrl+e to explain` markers in capture-pane output) and resolve them. ALL THREE require Enter as a SEPARATE `tmux send-keys` AFTER the digit — the digit alone selects, doesn't submit.
- **`ntm --robot-send --msg-file=PATH` displays long pastes (>~10 lines / >~800 chars) as a `[Pasted text +N lines]` placeholder, then waits for Enter to submit.** The recipe is two steps total: `--robot-send` per pane, then `tmux send-keys -t SESSION:0.N Enter` per pane. That's it. The TUI hint `paste again to expand` is a passive hint, not an instruction — IGNORE it. Once Enter submits, execution starts; the placeholder may LINGER in the visible buffer for a few seconds while the agent is already thinking. **DO NOT** interpret "placeholder still visible 5s after Enter" as "Enter didn't work" and **DO NOT** send Esc/Esc/Esc to "clear" the paste — Esc on a pane that has already started executing cancels the active turn, drops you into Claude Code's `Interrupt· What should Claude do` prompt, and now you've broken work that was fine. Verify cleanly by waiting **10-15 seconds** after Enter then capture-pane; if you see `↑ N tokens` / `↓ N tokens` / `Working…` / `Cogitated…` / any timer-bearing state indicator, the prompt landed and the agent is processing, regardless of whether `[Pasted text...]` is still visible higher in the buffer. Only re-send Enter if (a) 15+ seconds have passed, AND (b) capture-pane shows ZERO active-work indicators ANYWHERE in the visible buffer, AND (c) the input box is genuinely empty (no `[Pasted text...]` either). The Esc-cascade footgun is the most expensive mistake in this loop — confirmed April 2026: ~30 minutes wasted recovering from self-inflicted Esc-clears.

For one-shot reasoning swarms (`/modes-of-reasoning-project-analysis` and similar), the vibing-with-ntm marching-orders template doesn't fit — write a per-invocation dispatch script (`build_prompts.py` + `dispatch.sh` pattern) since the template assumes ongoing implementation work with bead-claim/file-reservation flows.

## Swarm conventions (adopted 2026-07-30 from the Agent Flywheel benchmark)

- **Bead IDs are threading anchors.** Use the bead ID everywhere a swarm artifact needs correlation: Agent Mail `thread_id`, message subject prefix (`[br-123]`), file-reservation reason, and commit message. Zero-cost; makes every audit trail joinable.
- **Stagger agent starts 30-60s apart** when launching multi-pane swarms — avoids the thundering-herd on beads claims, file reservations, and API rate limits.
- **PCR (post-compact reminder) is installed on both sides** — panes get the "re-read AGENTS.md" injection automatically after compaction. Do NOT also manually send "reread AGENTS.md" on every tick; reserve manual nudges for panes that visibly ignored the injected reminder.
- **SLB (two-person rule) is installed on both sides for swarm use** (`slb version` to check; per-project `slb init`). Its Claude Code PreToolUse hook is fail-closed and is deliberately NOT installed globally — wire SLB into swarms via AGENTS.md instructions (`slb run "<dangerous cmd>" --reason "..."`) where reviewer agents exist to approve. dcg remains the always-on mechanical layer; SLB adds the contextual human/agent-judgment layer on top.
- **Project bootstrap: one canonical AGENTS.md, imported by CLAUDE.md.** New multi-agent projects get an `AGENTS.md` (read by Codex/Gemini/other agents) and a project `CLAUDE.md` whose first line is `@AGENTS.md` — the official Windows-safe import (symlinks need admin/dev-mode). One file, every agent type reads it.
